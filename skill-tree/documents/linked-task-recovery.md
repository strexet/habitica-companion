# Linked task recovery

Linked unchecking is an explicit reviewed operation for one own completed Habitica Todo or an eligible completed Daily on the current verified account day. Native Companion recovery without game effects remains separate. The [history recovery panel](history-recovery.md), reviewed MCP contract and typed browser adapter expose the supported operation.

## Review and acceptance

`get_linked_task_recovery` accepts exact canonical `taskId` and retained `completionId`. Availability describes canonical eligibility and a verified original score receipt; local availability does not establish current native availability. `prepare_linked_task_recovery` requires both exact IDs, a stable `requestId` and `expectedRevision`. Preparation binds the canonical task, mapping and completion, full original complete-command hash/effect/source attempt, verified account, current revision and a fresh private Auth observation. Keep the original request ID after an uncertain preparation response.

The response returns a concrete expiring review, opaque `contextHash` and `review.reviewHash`. The review exposes task/checklist content for review, native identity and account/day. HP, MP, GP, XP and streak changes are all `unknown`. Habitica unchecking is not an exact reward refund. Obtain explicit user approval of the concrete inverse action and disclosure before `accept_linked_task_recovery` with the original `commandId`, `contextHash` and `reviewHash`. General task intent does not authorize an unreviewed inverse score.

Prepare/accept require `profile:read`, `tasks:read` and `habitica.tasks.write`. Reads require `profile:read` and `tasks:read`. Active Workspace consent and separate executor opt-in/global availability remain required for a new action. Private account authority comes from Auth; callers cannot supply an account selector. Existing Auth profile admission, upstream quotas, repair state and grant checks remain in force.

A review lasts at most sixty seconds, inside the private ninety-second single-use check lifetime. Acceptance checks the original source receipt again, current canonical revision, account, grant and gates. Auth repeats owner, completed state, full supported task/checklist fingerprint, value, Todo completion time or Daily streak, account day and Cron readiness immediately before dispatch. Shared/group/challenge copies, Habits, missing mapping, unknown readiness, prior-day Dailies and all unresolved task/tag/Cron/spell effects are refused. Legacy or expired score proofs remain unavailable; task state cannot replace original score proofs.

## Durable original result

Local migration `0014-linked-task-recovery.sql` adds a profile-scoped action table and `workspaces.linked_recovery_fence`. The server records the original down attempt ID, timestamp and exact private arguments before sending. A profile lease serializes recovery with executor/tag/Cron/spell work. The document trigger rejects competing canonical writes while the fence is held. Default production/preview gates remain off; linked recovery implementation performs no remote migration, deployment or activation.

A known original Auth `task_recovered` receipt permits one atomic canonical commit: a `LinkedTaskRecoveries` record plus the paired `TaskRestoration` for Todo or `OccurrenceCorrection` for Daily. Todo returns to Active with current task metadata retained. Daily reopens the same occurrence to Pending, retaining the previous terminal snapshot and original completion. No new score command, schedule edit, next occurrence, party operation or tag mutation is created. Original complete-command entries, dispatch events and completion events remain unchanged.

`get_linked_task_recovery_command` reads only the original command. The receipt read may look up the original Auth receipt and finish native bookkeeping after acknowledgement or local-save loss. The receipt read never resends down or reconciles success from a later task state. Dispatched non-200, malformed/lost responses and missing original receipts remain unknown and fenced. A saved native receipt survives a failed canonical commit; retry only finalizes that receipt. Confirmed receipts remain readable after gate changes. Changed connection/access epoch cannot authorize a new send; an unknown old connection stays fenced when the original connection receipt cannot be recovered.

Only a known pre-dispatch refusal releases a failed action's fence. A confirmed result clears the fence with the canonical receipt in the same D1 batch. Private check tokens and prepared payloads never enter public views or canonical exports; source and recovery attempt IDs, context and review hashes remain in retained canonical history. Capacity and retained-history limits refuse new actions before dispatch.

## Boundaries and verification

Habitica has no conditional score transaction across clients. An external edit can race the final read. Supported score/down changes task value and game resources, and Daily streak/history behavior; exact economic restoration is not guaranteed. The source is the reviewed [Habitica score implementation](https://github.com/HabitRPG/habitica/blob/develop/website/common/script/ops/scoreTask.js) and [server task scoring](https://github.com/HabitRPG/habitica/blob/develop/website/server/libs/tasks/index.js), inspected 2026-10-27 UTC.

Synthetic Miniflare composition covers actual reviewed MCP/browser endpoints, genuine original score-source receipts, Todo/Daily finalization, lost Auth acknowledgement, unknown provider response, failed canonical save, competing accepts, scope/profile isolation and stale/foreign/shared/day/consent/grant refusals. Neutral retained journals validate in C# and TypeScript. Typed browser tests reject identity/hash/resource/receipt tampering. Synthetic checks do not qualify live Habitica economics, hosted clients, physical devices, browser permission, real accounts or external-client races. See `skill-tree/history/validation/linked-task-recovery/result.json` for accepted evidence when the task closes.
