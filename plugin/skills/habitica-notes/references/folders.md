# Reviewed Notes folders

Folders are private single-level Notes containers. Each note has zero or one folder. Standalone folders have no project; project folders bind one exact canonical project. Names can collide and remain untrusted data. A project grant alone reveals no private folder or note content.

Use search_note_folders with relevant name terms and optional exact projectId/projectWorkspaceId or unassigned:true. Continue nextOffset with unchanged filters and returned expectedRevision. get_note_folder reads an exact folderId, current revision, immutable project/source scope and removal state. Multiple plausible matches require selection before mutation; a label never supplies identity.

Prepare a folder create with original requestId, notebookId, expectedNotebookRevision, expectedFolderRevision:0, operation:create and the complete requested name. Omit folderId for server allocation. A project folder additionally uses exact projectId/projectWorkspaceId and current own-project tasks:read. Standalone folders require only the independent Notes consent/read/write permissions. Folder scope cannot be changed by rename.

Rename/remove require the exact folderId and expectedFolderRevision from a fresh read. Rename supplies name. Remove omits name, removes only an empty folder and retains a tombstone. Any current member, including trash, refuses removal; never detach or delete notes as an implicit workaround. Nested/shared folders and whole-folder project moves are unsupported.

Inspect the preview's exact command/hash, folder identity, before/after name/project scope and lifecycle effects. Explicit unambiguous owner folder intent permits matching acceptance without repeated routine confirmation. accept_note_folder_command uses the original notebookId and preparedCommandId as commandId. Compare receipt payloadHash and exact revisions with the preview, then read the exact folder. If a later edit changed the folder, get_note_folder_command preserves original acceptance and separately labels currentFolder and metadataAtAcceptedRevision. A hash verifies the retained preview; current labels never reconstruct unavailable original metadata.

Create a note directly inside a folder through prepare_note_command folderId and full requested title/Markdown. Read the folder first and explicitly supply the same project association for a project folder. Move an existing note with operation:update, exact noteId/current revisions and folderId; use the matching explicit project patch when changing scope. Moving to a standalone folder from a project requires clearProject:true. Omitted Markdown preserves exact content. clearFolder:true detaches from the folder while retaining the project association. A project change with incompatible retained folder membership requires an explicit matching destination or clearFolder:true.

Verify note acceptance through the original note receipt and get_note at receipt.noteRevision. Compare contentHash and exact folder/project identities with the preview. folderContext labels the current folder name/revision separately from historical note membership. Search Notes with exact folderId or noFolder:true; noFolder and unassigned:true are independent filters. Retain complete text, line endings, content versions and original IDs.

For an Altai trip, resolve the exact existing project, create separate Hotels and Interesting places folders, and create one complete note per hotel/place containing the requested descriptions, reviews, hosts, activities and food details. Preserve all supplied details. The workflow creates no task, tag, score, reservation or message. Folder creation alone never authorizes capturing unrelated conversation.

After preparation uncertainty repeat the same requestId and identical arguments. After acceptance uncertainty recover get_note_folder_command or get_note_command with the original notebook/command IDs. Missing receipts remain unknown and never authorize replacement writes. Expired/revoked previews require a fresh exact read and explicit review for a new intent. Account or notebook changes cannot redirect original work.

Folder-aware browser-to-cloud Workspace adoption remains separately unqualified. No folder tool automatically copies browser folders, changes Notes consent, rebinds project references or publishes a package. Installed-host activation and actual model decisions require separate evidence.
