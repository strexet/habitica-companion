## Linked completed-task recovery

For explicit unchecking of an own linked completed Todo or eligible current-day Daily, use `get_linked_task_recovery` with the exact task and retained completion IDs, then `prepare_linked_task_recovery` with a stable request ID and expected revision. Local/source-receipt eligibility alone does not establish current native eligibility. Review the returned task, native identity, completion, account/day and unknown HP/MP/GP/XP/streak impact with the user. An exact reward refund is never promised.

Only after approval of that concrete inverse action, call `accept_linked_task_recovery` with the original command ID, context hash and review hash. On uncertainty, keep the original ID and use `get_linked_task_recovery_command`; never prepare or send a replacement score. Missing original score proof, shared/challenge tasks, prior-day Daily state, Cron uncertainty, changed consent/account/revision and competing effects must remain explicit refusals. Native skip correction and archival recovery remain separate zero-game-effect workflows. No party action, schedule update or next occurrence follows from recovery.

For archived tasks or terminal Daily recovery records without known task IDs, call `list_task_recovery_records` with `recordType: archivedTasks` or `terminalOccurrences`. Page using the returned revision and next offset. Current details and prior receipt references never establish a fresh game outcome. Use returned exact IDs with `get_task_recovery` and the existing reviewed native or linked recovery contract; no browser automation or identity guess is needed.

Adoption changes only correspondence and creates no rewards. Read the [exact correspondence guidance](references/habitica-correspondence.md) before adoption.
