# Durable Scheduled Web Push Reminders

## Current boundary

Implemented and published in the owner-selected [2026-10-29 production release](../history/releases/2026-10-29/README.md), with dedicated keys and service availability enabled. Ordinary committed profiles remain disabled; device/account consent and reviewed schedule acceptance remain required. Workspace owns separately reviewed one-time/recurring reminder intents, opaque device targets and configuration/delivery receipts. Auth alone owns encrypted endpoint/auth material, payload encryption, VAPID signing and provider requests. Saved task review metadata, foreground browser preferences, Web Push device consent and scheduled reminder intent are independent. No task, completion, review event, priority, recurrence, Habitica reward or gameplay command changes during scheduling or dispatch.

Browser sessions use /reminder-api and /reminders?taskId=...; agent clients use get_task_reminders, prepare_reminder_command, accept_reminder_command and get_reminder_command. The same Application boundary validates both surfaces. Browser device permission/subscription and the [dedicated setup UI](push-reminder-ui.md) remain separate consent surfaces. Task-read grants permit exact own-task reminder reads. Writes also require existing task-write grant plus independent active Web Push consent and explicit scheduled-reminders-v1 intent consent. Task/review writes never implicitly enroll reminders. Private Auth status reports dispatchAvailable separately from public subscription readiness, including the sender flag and contact configuration; public subscription status retains the existing strict client schema. Grant revocation invalidates unaccepted agent previews; an accepted durable reminder remains governed by independent profile/device consent and Workspace authority.

## Review and identity

Preparation binds exact task, Workspace revision, saved review cue, current source epoch, selected devices/subscriptions/revisions and intent hash. Server-issued schedule and command IDs, a ten-minute preview and latest accept token govern acceptance. Repeating the same request ID with matching arguments recovers the original preview; changed arguments conflict. Lost acceptance recovers the original command receipt without allocating a replacement intent. Acceptance and schedule changes share an atomic D1 batch. A configuration receipt confirms saved/scheduled intent only; no provider dispatch is implied.

Only one active schedule exists per task. Editing requires exact schedule/revision; cancellation retains history and works with dispatch disabled. A new or revised intent requires current task review metadata, active explicit devices and current separate push consent. Archived/completed/cancelled tasks refuse enrollment. Waiting/paused native tasks can carry optional review cues. The cue-changing review-event revision is retained separately from unrelated native task revisions; imported legacy cues use revision zero. Equivalent supported UTC encodings normalize without changing the task document. A later cue action, cancellation, archival, completion, source/connection epoch change or authority transfer stops unstarted old occurrences. Cancellation cannot recall an already dispatched message.

## Calendar and expiry

One-time reminders use the exact saved UTC review cue. Recurring intents add a validated daily/weekly/monthly rule, explicit HH:mm, supported IANA/UTC zone, inclusive end date and explicit DST policy. Nonexistent local times skip. Ambiguous local times require earlier, later or skip; no device-zone fallback or implicit fold choice exists. The first occurrence must match the saved review cue exactly. A recurring intent never advances the task review field. Civil calendars retain missing monthly dates and leap-day behavior from the shared recurrence evaluator.

Supported civil reminder dates are2020–2100. A repeating rule spans at most366 days; enrollment begins no more than366 days ahead. A cue expires one hour after the intended instant. Explicit preparation can schedule a reached cue within the remaining expiry window. Scheduler delays beyond expiry retain expired occurrence/device records rather than sending a stale catch-up burst. Provider TTL stays within the remaining one-hour window.

## Scheduling and receipts

The existing Workspace cron hook calls the reminder scheduler, gated independently from game execution. The scheduler reads persisted intents and the loaded canonical D1 snapshot, without Habitica polling. A separate per-profile lease, exact connection/authority checks and occurrence/device uniqueness serialize duplicate wakeups. Persisted last-wake ordering rotates profiles so unavailable targets do not permanently monopolize the bounded batch. The scheduler admits work for twenty-five seconds, with bounded pending private calls, and releases the owned lease. Unstarted records are rechecked against current task cue, schedule revision, device and consent before handoff.

Initial bounds are64 retained schedules, four explicit targets per schedule,2048 preparation/request identities and8192 occurrence/device records per profile. Exhausted capacity refuses further work without evicting dedupe identities. Each invocation considers at most twenty profiles and twenty dispatch attempts. Auth admits at most twenty attempts per profile/hour and retains at most8192 dispatch identities until profile deletion. Ordinary deployment profiles cannot enable the separately provisioned push flags.

A durable Workspace dispatched record and Auth admitted/dispatched claim precede provider traffic. Matching original attempts never send again. States distinguish scheduled, dispatched, accepted, refused, retryable, expired, cancelled and unknown. Every bounded retry retains a separate reduced attempt entry. Provider429 is a known refusal; Retry-After is respected, with at most three attempts and expiry taking precedence. Auth quota refusal also waits before another bounded attempt. Network failures, lost durable acknowledgement and uncertain provider5xx never retry an uncertain send. Recovery asks only for the original Auth receipt. accepted means HTTP201 from the push service; shown/read remain null. No exactly-once or human-delivery guarantee is made.

Reads expose bounded live pages of retained schedules/delivery attempts, including disabled schedules. Concurrent progression can change a live page; original configuration receipts remain the recovery authority. Canonical Workspace task archives do not include the separate reminder ledger. Removing a Workspace cascades reminder data; Workspace disconnect atomically pauses schedules and preserves independent account device consent. Auth disconnect pauses the matching connection and clears device material. Whole-profile deletion purges attributable reminder configuration, delivery and Auth dispatch rows through the private lifecycle binding. Failed cleanup remains a failure and cannot re-enable dispatch.

## Encryption and privacy

Auth validates the approved provider destination and exact subscription/VAPID binding again at dispatch. RFC8291 single-record aes128gcm uses fresh ephemeral P-256 ECDH and salt independently of VAPID. RFC8292 ES256 tokens bind the provider origin, a twelve-hour expiry and the separately configured contact URI. Generic encrypted payloads contain same-origin route and opaque task/schedule/occurrence identities, without task titles, bodies, account credentials or chat transcripts. Provider response bodies and credential-bearing request headers are not retained or logged.

Cloudflare Workers does not implement Fetch redirect:error. The sender therefore uses redirect:manual and explicitly refuses every3xx without following Location. HTTP404/410 erases the exact unusable subscription material and retains a revision tombstone. Old subscription identities cannot replace a current device. A provider-accepted generic notification can outlive cancellation/sign-out; no task-private text is included.

## Deployment and qualification

Apply Auth migration0011 and Workspace migration0013 before exposing the matching Worker code. Coordinated Auth/Workspace/MCP builds and lifecycle binding support are required. PUSH_ENABLED, Auth PUSH_DISPATCH_ENABLED and Workspace PUSH_REMINDERS_ENABLED remain false in committed/default/development profiles. No remote resource, key, cron setting or account was provisioned by local tests.

Production-module fake-clock and Miniflare/D1 controls cover one-time/recurring/DST identity, duplicate wakes, config rollback, changed/cancelled cues, profile/device revocation, expiry, cooldown/retry ceiling, original acknowledgement recovery, hourly quota, redirect refusal and independent Node crypto decryption/signature verification. An actual authenticated SDK fixture exercises schemas, preview/accept/read recovery, narrow scope and cross-account refusal. Full regression/build evidence resides in history/validation/push-scheduler/result.json. Operating-system delivery, iPhone permission, browser push/click handlers, hosted agent behavior and remote publication remain unqualified.
