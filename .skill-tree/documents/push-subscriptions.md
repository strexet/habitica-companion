# Web Push Subscription Contract

## Status and ownership

The owner selected Auth-owned custody on 2026-10-26. Subscription foundations are deployed. The owner-selected 2026-10-29 production release enables PUSH_ENABLED with dedicated vault/VAPID keys; ordinary committed profiles remain disabled. Device permission and separate account consent remain required. Auth owns the endpoint, p256dh/auth material, dedicated versioned AES-GCM keys and separate P-256 VAPID signing key. Workspace receives only opaque profile/connection/device/subscription identities, revisions, consent and status through PushService. No private service returns decrypted material, signs arbitrary content or proxies caller-selected URLs. Workspace reminder schedules and provider dispatch have independent consent and receipt contracts; their production publication is recorded in the [release report](../history/releases/2026-10-29/README.md).

The contract follows [W3C Push API security guidance](https://www.w3.org/TR/push-api/#security-and-privacy-considerations) and [WebKit Home Screen push prerequisites](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/). Provider-visible metadata includes timing, frequency and size. A subscription or a provider acceptance is not evidence of shown/read delivery. Later notifications must use task-neutral text and resolve private details only after same-origin authenticated navigation.

## Independent consent and browser boundary

Authenticated management access does not imply web-push-v1 consent. Grant and revoke use an expected consent epoch; subscriptions require the current enabled epoch and exact integration connection. OAuth grant revocation and Workspace-only disconnect do not revoke independent account-wide notification consent. Integration disconnect, credential replacement and profile deletion invalidate notification consent. Workspace reminder dispatch must additionally check current Workspace authority; deleting a Workspace must cancel the Workspace schedules without deleting account-wide subscriptions.

PwaPushBrowser is registered behind IPushBrowser; ChatGptIntegrationClient implements IPushSubscriptionClient using the existing tab-only management bearer. No Settings or task control uses the foundation yet. PrepareAsync imports the module and reads capability before an enabled user action is rendered. SubscribeAsync never lazily imports a module. The first subscribe browser action requires current userActivation, explicit reminderConsent and installed standalone capability, then calls Notification.requestPermission before awaiting service-worker inspection. Missing APIs, denied/dismissed permission, insecure context and noninstalled use return explicit states. Import and page load request no permission. Current status reports browser permission without requesting permission; UI integration must reconcile permission revoked outside the app and remove the server target explicitly. The browser cannot notify Auth of revocation while the browser is closed.

Existing browser subscriptions are reused only with the same applicationServerKey. A changed key requires an explicit recovery flow; the module never silently replaces or deletes a subscription. Local unsubscribe checks the reviewed endpoint fingerprint before acting. Browser endpoint/auth fields are a transient upload only; callers must not put endpoint/auth fields in persistence, diagnostics, rendered copy or task commands. Browser and server unsubscribe are separate effects: revoke the server target first, then inspect local removal; an uncertain local result must not reactivate server delivery. User-agent-owned subscription changes can race inspection; physical platform semantics remain a release check.

## Auth API and receipts

Own-profile routes under /profiles/{profileId}/push expose GET status, POST consent/subscribe/unsubscribe and GET commands/{requestId}. Every write binds an explicit UUID request, connection and expected consent epoch or device revision. A subscribe additionally requires userVisibleOnly=true and a separately generated device UUID. The client rejects stale session responses, foreign identities, unknown response fields, mismatched revisions and oversized responses. The client sends no automatic retry. Cancellation propagates; an uncertain write recovers through the original request ID before another change. A missing/expired receipt never proves a write failed.

D1 batches commit the mutation and original receipt atomically, using in-transaction profile/token/connection, consent and revision guards. [D1 batch semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/) roll back the batch on failure. Duplicate IDs with different payloads conflict. Exact duplicates return the original result even after later revocation, without resurrecting authority. Active endpoints have one profile/device owner. Management traffic retains the existing 30-per-minute profile budget; no separate unlimited lane is introduced.

There are at most 64 lifetime device records and 1,000 retained receipts per profile. Content-free device tombstones preserve monotonic revision after unsubscribe/revocation/expiry and prevent replay after receipt expiry. Capacity refuses a new write without partial mutation. Tombstones and consent metadata remain until integration profile deletion. Original receipts expire after thirty days; reads exclude expired receipts immediately, and bounded cleanup removes rows. Active envelope expiry purges material and increments device revision; per-profile inspection covers the entire bounded device set. Global scheduled cleanup processes at most 128 expired devices and receipts per invocation.

## Secrets, endpoint validation and lifecycle

AES-GCM uses random 96-bit IVs and associated data containing purpose, envelope schema, profile, device, revision and key version. Push keys must differ from every configured Habitica credential/identity key and the VAPID private scalar. Configuration checks prove the public/private signing keys match using Web Crypto. Missing, malformed or reused keys refuse new grants/subscriptions while status and revocation remain available. Retain previous push decryption keys until a separately qualified rotation removes every dependent envelope; no rotation or real provisioning is implemented by the subscription task.

Endpoints are canonical HTTPS, at most 2,048 characters, with a non-root path and no credentials, explicit nondefault port, fragment or query. Accepted hosts are fcm.googleapis.com, updates.push.services.mozilla.com, web.push.apple.com and a single subdomain of push.apple.com. [Mozilla production endpoints](https://mozilla-services.github.io/autopush-rs/#production) and [WebKit push endpoints](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) document the corresponding providers. The application allowlist deliberately limits provider support beyond the general protocol. IP/private/unknown destinations and lookalike suffixes are rejected. The bounded provider policy can refuse a valid unfamiliar browser provider; support requires a reviewed extension. Subscription setup makes no provider request. The later sender must use manual redirect handling with explicit3xx refusal, repeat destination validation at dispatch and purge unusable 404/410 targets.

Unsubscribe, consent revocation, expiry and integration disconnect clear endpoint hashes and ciphertext/key metadata without deleting tasks. Profile revocation blocks private/public active-profile checks before cleanup. A cleanup failure reports pendingCleanup and permits an explicit cleanup retry; blocked profiles cannot reenroll until cleanup succeeds. Credential replacement fences the old connection immediately and clears old-connection push material. Profile deletion removes all three push tables. Workspace export and ordinary task/Notes/private-sync storage never receive push material; own status is a minimal metadata view, excluding endpoint hashes, ciphertext and keys. Operational errors are sanitized and no subscription payload is logged. Hosting backups retain the provider recovery lifecycle; clearing active rows does not erase downloaded files or provider backups.

## Qualification boundary

Authenticated Miniflare tests apply all Auth migrations and cover encryption/AAD, configuration separation, independent consent, account/device/connection isolation, CAS/concurrent duplicates, rollback, receipt expiry, capacity, revocation, cleanup failure/retry, Workspace export/disconnect/deletion and the restricted service binding. Browser API fixtures cover permission grant/deny/dismissal, standalone/capability refusal, key mismatch, local unsubscribe fencing and sanitized errors. C# checks cover exact transport/receipt identity, stale sessions, cancellation and no automatic retries. The controls are synthetic; physical iOS permission persistence, browser revocation races, actual push dispatch, delivery while closed, lock-screen appearance, click routing, live MCP use and publication remain unrun. No changed UI route is qualified by the subscription foundation.
